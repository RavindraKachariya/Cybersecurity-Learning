# 12.Nmap Scripting Engine (NSE)

---

## **What is Nmap Scripting Engine (NSE)**

The Nmap Scripting Engine (NSE) is **not just a scanning add-on**, it is a **logic layer** on top of Nmap.

Think of it like this:

- Normal Nmap answers:
    
    👉 *“What is open?”*
    
- NSE answers:
    
    👉 *“What does this service allow, expose, or misconfigure?”*
    

NSE scripts allow Nmap to **interact with services**, not just detect them.

---

## **Why NSE Exists**

Traditional port scanning tells you:

- Port 80 is open
- Port 22 is open

But it does NOT tell you:

- Is SSH weakly configured?
- Is HTTP vulnerable?
- Is SMTP an open relay?
- Is SMB leaking system info?

NSE exists to:

- **Ask intelligent questions** to services
- **Automate repetitive security checks**
- **Reduce manual testing effort**

---

## **Important Safety & Legal Context**

Before touching NSE, always understand this:

- NSE scripts can be **intrusive**
- Some scripts actively:
    - Authenticate
    - Enumerate users
    - Trigger vulnerabilities
- Running NSE **without permission** can:
    - Break systems
    - Trigger IDS/IPS
    - Cause legal issues

👉 NSE should be treated as **active testing**, not passive scanning.

---

## **How NSE Scripts Actually Work**

 

1. Nmap detects open ports
2. NSE scripts attach to those services
3. Scripts send protocol-specific requests
4. Responses are analyzed
5. Results are printed under **Host script results**

This is why NSE output appears **after port scan results**.

---

## **Execute Individual Scripts (`-script`)**

### **Command**

```bash
nmap --script whois.nse scanme.insecure.org
```

### **What Happens Internally**

- Nmap identifies the target
- NSE loads `whois.nse`
- Script contacts an **external whois database**
- Information is retrieved and parsed
- Output is shown under **Host script results**

### **Why Individual Scripts Are Useful**

- Precise control
- Minimal noise
- Safer in restricted environments
- Ideal when you know **exactly what you want to test**

This is the **recommended approach for beginners**.

---

## **Understanding Script Results Output**

Script results always appear under:

```
Host script results:
```

This helps you separate:

- Port scan data
    
    from
    
- Script execution data

This separation is important when analyzing large scans.

---

## **Execute Multiple Scripts**

### **Command Using Wildcards**

```bash
nmap --script"smtp*" 10.10.1.44
```

### **What This Really Means**

- Nmap searches its script database
- Finds all scripts starting with `smtp`
- Executes them **one by one**
- Results are combined

### **Why Wildcards Are Powerful**

Pros:

- Covers an entire protocol
- Saves time
- Finds multiple issues at once

Cons:

- Can be noisy
- Can trigger IDS
- Can take longer
- Can stress services

👉 Use wildcards **only when authorized**.

---

### **Comma-Separated Scripts**

```bash
nmap --script script1,script2,script3 target
```

This method is safer than wildcards because:

- You choose exact scripts
- Predictable behavior
- Less risk

---

## **Script Arguments (`-script-args`)**

Some scripts require **input values**, such as:

- Usernames
- Passwords
- Paths
- Timeouts

These are passed using:

```bash
--script-args
```

This allows scripts to behave **dynamically**, not statically.

(Exact arguments depend on the script — always check documentation.)

---

## **Script Categories**

### **Why Categories Exist**

Nmap includes **hundreds of scripts**.

Running all of them manually is impractical.

Categories group scripts by **intent**, not protocol.

---

### **Understanding Each Category**

- **default**
    
    → Safe, commonly useful checks
    
    → Low risk, good starting point
    
- **safe**
    
    → Designed to avoid service disruption
    
    → Minimal interaction
    
- **discovery**
    
    → Focuses on identifying systems deeply
    
    → Hostnames, versions, shares, configs
    
- **auth**
    
    → Tests authentication mechanisms
    
    → Login methods, credentials, access
    
- **vuln**
    
    → Checks for known vulnerabilities
    
    → High-value, but higher risk
    
- **intrusive**
    
    → May alter system behavior
    
    → Use only with permission
    
- **malware**
    
    → Looks for backdoors and infections
    
- **external**
    
    → Contacts third-party services
    
    → Whois, IP reputation, etc
    
- **all**
    
    → Everything
    
    → Rarely used in real environments
    

---

## **Execute Scripts by Category**

### **Command**

```bash
nmap --script default 10.10.1.70
```

### **What Happens**

- Nmap loads **all scripts** in the default category
- Scripts run after port discovery
- Results are consolidated

This is why category-based scans:

- Take longer
- Produce more output

💡 **Shortcut**

```bash
-sC
```

is exactly the same as:

```bash
--script default
```

---

## **Execute Multiple Script Categories**

This is where NSE becomes **very powerful**.

### **Comma ( , )**

```bash
--script malware,vuln
```

Means:

👉 Run **everything from both categories**

---

### **AND Operator**

```bash
--script"default and safe"
```

Means:

👉 Run scripts that belong to **both categories only**

This reduces risk.

---

### **OR Operator**

```bash
--script"default or safe"
```

Means:

👉 Run scripts that belong to **either category**

More coverage, more noise.

---

### **NOT Operator**

```bash
--script"not intrusive"
```

Means:

👉 Exclude dangerous scripts

This is commonly used in professional testing.

---

## **Troubleshoot NSE Scripts (`-script-trace`)**

### **Command**

```bash
nmap --script default --script-trace 10.10.1.70
```

### **What Script Trace Shows**

- Every packet sent by scripts
- Every response received
- Script execution flow

This is **script-level debugging**, not normal scan debugging.

---

### **Why Script Trace Is Important**

- Script fails silently → trace explains why
- Network blocks script traffic
- Protocol negotiation fails
- Authentication errors

Because output is huge, always redirect:

```bash
> trace.txt
```

---

## **Update the Script Database (`-script-updatedb`)**

### **Why This Is Needed**

Nmap maintains a **script index database**.

When you:

- Add new scripts
- Remove scripts
- Update scripts manually

Nmap will **not recognize changes** until the database is rebuilt.

---

### **Command**

```bash
nmap --script-updatedb
```

### **What It Does**

- Scans script directories
- Rebuilds category mappings
- Updates internal references

This step is **mandatory** after script changes.

### Api with nmap

```jsx
nmap --script shodan-api --script-args shodan-api.apikey=YOURKEY <target>
```
